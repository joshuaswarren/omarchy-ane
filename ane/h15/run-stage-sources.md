# ane_h15 stages 4 and 5: where each claim comes from

Every register, address and sequence below carries its source, pinned to a commit or a file hash, and says whether it is an H15 observation or an inference from another generation. Nothing in stage 4 or 5 has run on hardware.

## H15 observations (T6030, 16-inch J516S, macOS 14.7 / firmware 27.0)
- Stage 0, 1 and 2 results: PR 175 on joshuaswarren/omarchy-ane, comment of 2026-10-23T01:57Z (Chris Kearney). CPU_STATUS 0x0030002a, RVBAR_LO 0x1, RVBAR_HI 0x100, MBOX_A2I_CTRL and MBOX_I2A_CTRL 0x20001, five pmgr words ACTUAL=0xf, ANE DART nodes disabled. This is the only H15 register measurement. It is the source of `rvbar_expect` and of the preflight values.
- DART window addresses (0x309800000, 0x309810000, 0x309820000, 0x309804000, 0x4000 each) and `dart,t8110`: 27.0 ADT facts recorded from the shipped system, in `data/ane-soc/t6030.json` (source S1 there, receipt sha256 04fe38b8…ffdb84). Not measured on silicon by us. The names `ttbr0..3` in that file are the summary's, not roles from the ADT.

## Inference from another generation (not measured on H15)
- STOPPED is the "started" flag, bit 1 of CPU_STATUS; RUN is CPU_CONTROL bit 4: m1n1 `proxyclient/m1n1/hw/asc.py` at 97820568035b8d7035c68e4126f203d86c76abe4, lines 12-24 (`R_CPU_CONTROL.RUN = 4`, `R_CPU_STATUS.STOPPED = 1`, `RUNNING = 0`) and 77-85 (`is_running()` is `not STOPPED`, `boot()` is `CPU_CONTROL.set(RUN=1)`, `shutdown()` is `set(RUN=0)`). Observed on the M6: the RUN write took CPU_STATUS 0xa to 0x8 (STOPPED cleared, RUNNING never read 1), boot 235c8ff4, private dmesg log sha256 74e9b666c3d03b8f07997e33253ea9734b1886999061d801f196ddc8d14bb48b.
- Start and stop sequence (read CPU_CONTROL, OR 0x10, write; stop: clear bit 4, write, re-read, clear bit 5, write): macOS 27.0 behaviour on the T8152, recorded in a private lab note (sha256 d383f6741bf98b1a8140a72c1dde38e333d19f9d87c91334b8f21068e84f5857). That is the M6's ascwrap-v8. The H15 ANE is `iop,ascwrap-v6`. That the same bit 5 step applies on H15 is an inference. m1n1 clears only bit 4.
- Reading CPU_CONTROL: `ane_h15_read_ok()` keeps it off the stage 2 allowlist ("hostile on T6001", from the T6021 work, `ane/t6021/ane_t6021.h` at 16cfa8720b80677dbcdf8fd1d04077a8b72768bf). Stage 5 reads it once, in a dedicated function, before any write, because the macOS sequence is a read-modify-write and a blind write could clear bit 5. No H15 read of it exists. A fault here happens before anything is written.
- Mailbox registers: CTRL words at wrapper + 0x110 and + 0x114 (read on T6030 in PR 175). Receive registers I2A_RECV0 at + 0x830 and I2A_RECV1 at + 0x838, 64-bit, pop on read: `ane/t6021/ane_t6021.h` at 16cfa8720b80677dbcdf8fd1d04077a8b72768bf lines 138-147 (T6021, observed there), `drivers/soc/apple/mailbox.c` in omarchy-linux at 57f8f6deaa3a5ee97d820dc97844bf448e4d7fed lines 39-47 and 405-430 (`APPLE_ASC_MBOX_I2A_RECV0 0x830`, the v4 layout the other T6030 ASCs use). Not read on H15; stage 5 reads them only if I2A leaves EMPTY.
- DART registers (PARAMS3 +0x08, PARAMS4 +0x0c, PROTECT +0x200, PROTECT_LOCK +0x208, ENABLE_STREAMS +0xc00, TCR +0x1000 + 4*sid, TTBR +0x1400 + 4*sid, one TTBR per stream, up to 256 streams): `drivers/iommu/apple-dart.c` in omarchy-linux at 94fb23346d522edf53722357c426a3e58030beea, lines 91-148 and the t8110 hw table (`ttbr_count = 1`, `max_sid_count = 256`). Stage 4 reads 64 streams. Not read on H15.
- Why a DART scan comes before a core start: macOS behaviour on the M6 ANE DART (a private lab note, not in this repository): macOS programs TEXT and DATA mappings and enables the stream before RUN. The M6 board read (boot 5f6aa530, PR 183; stated in the body of PR 185): every ENABLE_STREAMS word 0, so iBoot left no stream enabled. Stage 4 measures the same on H15.
- The map_fw step: the M6 module's `ane_h18_map_firmware()` in PR 185 (`h18-dart-map-stage`): `iommu_paging_domain_alloc`, `iommu_attach_device`, `iommu_map` of TEXT (read) and DATA (read+write), undo on failure. PR 185 states it was not checked on the board when written; a later report, relayed without a receipt, says the run then showed HELLO and EPMAP from the firmware and accepted replies. The segment layout (TEXT phys 0x100014e8000 size 0xc4000 at 0x10000000000; DATA phys 0x100030c4000 size 0x2ac000 at 0x100000c4000) is the saved M6 ADT (a private note; ADT sha256 6d6827271263e12da4ae103c18708051156586aced2a0472ff78d5985183d254) and reproduced by `h15-segments.py`. On T6030 nothing is measured: the IOVAs are derived from RVBAR (INFERRED), and the physical addresses must come from the live ADT of the tester's boot.
- Why `fw_seg` is a parameter: m1n1 at de2c1a600130562827bc961cd10d5c18c687a66f (HEAD of the local checkout used here), `src/kboot.c` `dt_reserve_asc_firmware`, writes asc-firmware reserved regions and `iommu-addresses` only for dcp, dcpext and ave. Nothing does it for the ANE, so the Linux device tree has no source for the physical addresses.

## Stage 6 (rtkit)
- The message sequence and constants (type in bits 59:52, HELLO 1, HELLO reply 2, STARTEP 5, SET_IOP_PWR_STATE 6, IOP power acknowledgement 7, endpoint map 8, SET_AP_PWR_STATE 0xb, power states OFF 0, SLEEP 1, QUIESCED 0x10, ON 0x20, minimum version 11, application endpoints from 0x20): `drivers/soc/apple/rtkit.c` in omarchy-linux at 94fb23346d522edf53722357c426a3e58030beea (the constants near the top, `apple_rtkit_*` handlers). This is the Linux driver for every other Apple RTKit coprocessor, an inference for the ANE.
- The session as run on the M6: `ane/h18/ane_h18_main.c` on main at 3de0e8a745ccb9983df52231ff71a990741c37eb (`ane_h18_rtkit_step`, the shutdown block of `ane_h18_stage_boot`; PR 186 and 190 and the later h18 PRs). Its board results (firmware HELLO version 12, endpoints 0, 1 and 0x20, IOP power ON acknowledgement 0x20, AP power ON sent and acknowledged, clean shutdown and stop) are reported in those PRs; this author read the PRs, not a receipt.
- The transport: the T6030 ANE is `iop,ascwrap-v6`; the wrapper mailbox CTRL words read 0x20001 (PR 175). Send registers at +0x800 and +0x808 and receive registers at +0x830 and +0x838 are the apple-mailbox v4 layout (`drivers/soc/apple/mailbox.c` in omarchy-linux at 57f8f6deaa3a5ee97d820dc97844bf448e4d7fed, lines 39-47 and 405-430; `ane/t6021/ane_t6021.h` at 16cfa8720b80677dbcdf8fd1d04077a8b72768bf lines 138-147 for the T6021). INFERRED for the T6030 ANE. The M6 ANE uses a Postoffice (`msgbox-using-postoffice` in its ADT); whether the T6030 does is not in our ADT summary (no mailbox node, no such property), so the mailbox transport is the open question for stage 6.
- Never answered, as on the M6: the crash log buffer request on endpoint 1 and every message of an endpoint other than 0.

## Stage 7 (chan)
- The shipped system's 27.0 (mac18g) behaviour for ane-type 0xc0 (the T6030, SoC name "h15g"), recorded in a private lab note (not in this repository). The SCRATCH register offsets are the eight words 0x1840050, 0x1840054, 0x1840058, 0x184005c, 0x1840060, 0x1840064, 0x1840068, 0x184006c (engine-relative), the CPU_CONTROL offset 0x1400044 (matches the SoC row here), the CPU_STATUS offset 0x1400048 and the doorbell register offset 0x1844000 (the doubleword the shipped system writes `1 << bit` to), and the config size 0x380000. The M6 (ane-type 0x310) differs: SCRATCH at engine + 0x18a0024, doorbell 0x18a4000. Nothing of this was read or written on an H15 part.
- The sequence (zero SCRATCH0..7 once before RUN, read SCRATCH0/1/3/4 after READY, allocate IPC and HEAP, fill the 0x174 byte init block, `dsb st`, SCRATCH0, SCRATCH1, SCRATCH7 = 0xf7fbdff9, poll SCRATCH7, read the table address, create the channels, write SCRATCH3 = 0x08042006 and wait for 0) is the same on every SoC type; the block layout is the T6021 one (`ane/t6021/ane_t6021_boot.h`) and the M6 module's (ane/h18, PRs 195, 196 and 205, whose board result is that the firmware published a table in 2 ms). This module does not zero SCRATCH (the firmware already published its requests) and never pulses SCRATCH7.
- Never answered or written: the firmware's crash log request, any SCRATCH word but 0, 1, 3 and 7, and the doorbell without `chan_cmds=1`.

## What the stages can and cannot show
- Stage 4: whether a stream is enabled and translating, which stream, and whether the block is locked. Not that the mapping covers the firmware, nor that the core would run.
- Stage 7: whether the firmware accepts the macOS handshake at these SCRATCH offsets and publishes a channel table, and whether the restartable stop works once the channels exist (the M6 wall). A timeout at `handshake-no-table-address` points at the offsets or the init block, not at the RTKit session.
- Stage 6: whether the firmware speaks RTKit on this mailbox, and whether the session and shutdown complete. Silence ("rtkit-no-hello") would point at the transport, not at the sequence.
- Stage 5: whether the core leaves STOPPED, whether it posts a message, and whether clearing RUN stops it. Clearing RUN did not stop the core in either M6 case (running firmware: status `0xd`; no firmware mapped: `0x8`). A core that runs firmware stopped only after RTKit power messages (stage 6). So clearing RUN does not guarantee STOPPED, and `core-not-stopped` alone establishes neither that firmware ran nor that unloading is safe. With no mapped DART, silence is the expected result and does not mean the core is broken.
