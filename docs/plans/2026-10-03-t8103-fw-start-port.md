# T8103 ANE firmware start: port design from the T6021 path (2026-10-03)

Status: design only, nothing built. Gate: the M2 perf-mode A/B (CH_PROPERTY_WRITE 0x10aa=1, `fw_perf_mode`). If perf mode does not move exec time on T6021, the clock lever is not worth steps 1-5 below. A positive M2 result motivates the port but does not prove the T8103 case.

Why this lever: on jwm1 (T8103, Linux) the whole-encoder is ~139.4 ms vs 113.27 ms on macOS (0.81x). The clock/DPE/PPT state is owned by the ANE firmware (`CPowerControlServiceAneH13`, `CAneEngineExeLoop::setPerfMode`); AP-side replay of TurnOnDPE latched but changed nothing (H164), and no AP-reachable perf register was found (H165). The firmware is the remaining lever.

Address-space model (inference from H166/H167 and the ADT segment-ranges, not yet exercised): RVBAR entry is a physical address and the TEXT fetch does not use the DART; the DATA segment is reached through the DART at the low 32 bits of the ADT remap (mask 0xf00000000 | 0xbc000, so IOVA 0xbc000, immediately after TEXT vmsize 0xbc000). The T6021 alias recipe (iommu_map TEXT at the entry IOVA) therefore does not carry over for TEXT; only DATA (and every fw-visible heap/IPC surface) is DART-mapped.

Firmware evidence for that model (offline, H13 13.5 image vs selene 13.5, `ffwMMUInit`): the H13 function (0x22e54) calls `RTK_mmu_virt_to_phys` on its own address and derives the DRAM mask from the physical result: bit 40 set gives 0x1f000000000 (T6001), else bit 35 set gives 0xf00000000 (T8103), stored at [0x4f0738]. The selene function is a bare tail call with no mask logic. So the H13 fw has its own ASC MMU (`RTK_mmu_*`), computes the mask from where it was loaded (0x8_0093_8000 has bit 35: mask 0xf00000000, equal to the ADT `asc-dram-mask`), and ORs it onto bus addresses; this is the mechanism behind "fetch is physical, data goes out as mask | address through the DART". Consequence (inference): the host must publish IOVAs below 4 GiB (the DART aperture) and the fw adds the mask; publishing mask-included values would double-apply it. Function-level comparison (register-normalized, `symcmp`): 949 of 1288 same-named functions are identical H13 vs selene 13.5; the ChMan boot function (0x6268 in both) differs only in stack frame layout and register allocation, with the same constants (wake 0xf7fbdff9, READY site), so the T6021 scratch protocol applies. `CPlatformEnvironment::InitPlatform` (H13 0x6e48) differs from selene only in the SoC base it loads: H13 `mov x8,#0x6b000000` / `mov x1,#0x6b000000` (platform block = 0x26b000000 = engine 0x26a000000 + 0x1000000) vs selene `0x85000000` (0x285000000 = engine 0x284000000 + 0x1000000), plus a virt-to-phys step selene adds for one pointer. Same relative layout, so the host-side offsets measured in H166/H168 (SCRATCH +0x1840048, mailbox +0x1408000, doorbell +0x1844000) are the T6021 ones rebased on the T8103 engine. Still to be read: `CLoggerSharedBuffer` ctor, `CConfigDrvHxInit`.

## 3. Module shape
New `ane/h13/ane_t8103_fw.c` (the legacy `ane` module and the fw module cannot both run: once the ASC runs, the legacy TM island path stops serving, measured on T6001). Selected by modprobe option file (fw module on, `ane` blacklisted), the same switch the M2 uses; removing the option file and rebooting restores the legacy path. Binds `apple,t8103-ane`. Hard rule kept from H164: all ANE/pmgr MMIO via `ioremap_np`, first access >= 3 s after power-up.

## 4. Staged windows (each write step needs w73's OK; any reset = record the stage and stop)
1. Probe stage (read-only): module loads, powers via genpd, maps the engine NP, re-reads RVBAR/CPU_STATUS/SCRATCH/doorbell, verifies the 47 TEXT pages against the pinned payload. No write.
2. DATA stage: allocate and fill DATA, `iommu_map` at IOVA 0xbc000 on the shared domain, read back through the CPU, verify. No device write beyond the DART domain (Linux-owned page table).
3. RUN stage: clear SCRATCH, pulse SCRATCH7, `CPU_CONTROL` 0 then 0x10, poll SCRATCH7 for READY 0x08042006 (T6021: instant). Rollback = reboot.
4. ChMan stage: publish init structure, wake, poll DONE, validate the IPC table (the T6021 `chman_check`).
5. Command stage: legacy ChMan commands (alloc, PROG_LOAD, CREATE_PROCESS, PROCEDURE_CALL) with a trivial program; then `0x10aa=1`.
6. Encoder stage: run the whole-encoder through the fw path, compare digest `554a3d66` and time against 139.4 ms (target <= 116 ms, macOS 113.27 ms).

## 5. Open items, each with the cheapest discriminating measurement
- O1 TEXT fetch path: confirm RVBAR is a physical fetch (stage 3 reaching READY with TEXT unmapped in the DART is the test; a DART fault register read after RUN names a wrong model). Fallback: identity-map is impossible (32-bit aperture), so a failure means the segment map lives ASC-side and needs the ADT of the 13.5-stub boot (m1n1, no macOS needed).
- O2 DART error registers: +0x40/+0x50 read nonzero at rest in H167 and are not confirmed as error status on this DART; identify the right ones from apple-dart.c before using them as a fault oracle.
- O3 Init-structure consumer: diff the field reads of the H13 13.5 image next to its READY site against selene's fn 0x71A4 read-set (offline, both images are in the notebook). Until done, stage 4 cannot publish.
- O4 CPU_CONTROL +0x1400044 read behaviour on T8103 (write-only on T6021; read cost a reset on T6001).
- O5 Program format (largest): the encoder is driven today as H13 HWX through libane on the TM path. The fw PROG_LOAD needs the package the H13 fw accepts; the M2 converts H14 HWX with `tools/hwx_h14_to_anec.py`. Establish the H13 equivalent from the 13.5 image's program loader and the kext, then convert the existing encoder bundle. Without this the fw path cannot run the encoder, so the lever cannot be measured on the encoder even if the boot works.
  Offline evidence (H13 13.5 vs selene 13.5, `symcmp`/`fdiff`): the H13 firmware verifies a PROG_LOAD far more strictly than selene. `verifyProgram` is 229 insns on H13 vs 67 on selene, `verifyProgramSection` 139 vs 2 (a stub on selene), `checkBarEachAneOp` 254 vs 130, `verifyGenericSection` 107 vs 47, `verifyBAR` 188 vs 172. The loader proper (`CAneServer::InitProgrm`, `LoadProgram`, `CAneProgramManager::AddProgram`) is the same code with only data-address differences. So what the M2 path feeds selene (the ANEC package from `hwx_h14_to_anec.py` wrapped by `ane_rtclient_load_program`) cannot be assumed to pass H13 verification. `verifyProgram` (H13 0x4b9f8) shows the `sCSneCmdProgramLoad` skeleton the host must build: sections as {flag byte, pointer, size} groups at +0x08/+0x20/+0x28 (generic), +0x38/+0x50, +0x68/+0x80 (descriptor-prop input), +0x98/+0xb0 (operation section), +0xc8/+0xe0 (procedure section list), +0xf8/+0x110 (kernel-prop, optional), +0x128/+0x140 (descriptor props); each flag byte bit0 must be set and its pointer nonzero, then `verifyGenericSection`, `verifyOperationSection`, `verifyProcedureSection`, `verifyKernelPropSection`, `verifyDescriptorPropSection`, `verifyDescriptors`, `verifyBAR`. This is the structure the macOS kext builds from an H13 HWX, so the work item is to port that packaging (kext `AppleH11ANEInterface` program-load builder) rather than reuse the M2 converter. Next offline step: decode each verify* function into a field-level spec and check the existing encoder HWX against it.
- O6 Whether the fw clock request needs the host's CSNE/PerfControl link or the fw issues it alone per request (perf mode flag test at pushToHW +0x640, per the fw-vs-t602x receipt section 7): measurable only after stage 5.

## 6. What this does not claim
Nothing here is a parity claim. Encoder stays a loss (0.81x, 139.4 vs 113.27 ms) until stage 6 produces a paired number.
