## Register contract (authoritative source: torvalds
drivers/iommu/apple-dart.c; host trees are stripped, no apple-dart.c
on jw14m2; running driver matches on every observable)

- Overlay compatible "apple,t6020-dart","apple,t8110-dart"; mainline
  of_match has no t6020 entry → binds apple_dart_hw_t8110. Running
  kernel prints extra "locked:" field (fork extension); DART probe
  lines: `pagesize 4000, 16 streams, bypass 1, locked: 0, AS 42 -> 42`.
- TCR @0x1000+4·sid: TRANSLATE_ENABLE=BIT(0), FOUR_LEVEL=BIT(3).
  Live: 0x9 on all three darts ✓.
- TTBR @0x1400, ttbr_count=1/sid: VALID=BIT(0); encode
  `valid | (pa >> 14) << 2`. Live: 0x10012395 on all three darts
  (one shared io-pgtable) → pa = **0x10012394000**, 16 KiB-aligned ✓,
  inside System RAM ✓ (decoded with the mainline shift14/afs2 formula;
  the shift12/afs2 alternative decodes to 0x40048e5000 which is NOT in
  /proc/iomem RAM — rejected). NOTE: DRAM on this box sits at PA
  [0x10001f74000, ~0x117b9403fff] ≈ [1.024 TiB, 1.119 TiB], 94.9 GiB —
  the earlier "< 96 GiB ⇒ impossible" reasoning was inverted by the
  real /proc/iomem ranges (Main's check).
- ERROR @0x100: FLAG=BIT(31), STREAM=27:20, CODE=14:0, NO_PGD=BIT(1);
  FAULT_ADDR @0x170/0x174. Live ERROR=0 (17:48 fault handled+cleared),
  FAULT retains 0x100000dca10 ✓. dart1/dart2 ERROR low bits stale
  (0x00f00000/0x00700000, flag clear — benign residue).
- +0x100 on T8020 layout would be TCR — the old "+100 is TTBR" reading
  is retracted; irrelevant for t8110 layout anyway.
- PROTECT @0x200 = 0x2 on dart0, 0 on dart1/2: TTBR/TCR write-protect
  bit (BIT(0)) CLEAR everywhere — but raw TTBR writes remain forbidden
  by lane rules; everything below is driver-managed iommu_map().
- io-pgtable (drivers/iommu/io-pgtable-dart.c, APPLE_DART2): u64 PTEs,
  VALID=BIT(0), pa = (pte & GENMASK(37,10)) << 4, SUBPAGE_END bits
  51:40 = 0xfff on mapped leaves; levels indexed pgd[iova>>36],
  mid[iova>>25], leaf[iova>>14] (11 bits/level, 16 KiB tables).
- Domain: default DMA domain, aperture [0, 2^42) (ias=42 > 36 ⇒
  FOUR_LEVEL, matching TCR bit3), apple_dart implements
  .map_pages + .iotlb_sync_map (driver flushes DART TLB) and
  .iova_to_phys.

## Boot-law placement

Kext lifecycle (rvbar-lifecycle 6288b0b): RVBAR bit0 SET ⇒ the RVBAR
write branch is SKIPPED ("skipRVBARwrite, NOT skipCPUrelease"). The
ASC therefore fetches at the latched entry 0x10000000000, and the only
lawful placement for the fw image is an ALIAS AT the entry IOVA in the
same driver-managed table. The unlatched branch (no alias needed:
compose(fw_iova) = 0x008103ffff800001) is handled by the existing
boot.c path.

## Collision invariant (reservation substitute)

No runtime IOVA-reservation API is exported on this kernel
(Module.symvers checked). NOTE (Main correction): a DT reserved-memory
`memory-region` node reserves PHYSICAL RAM, not DMA IOVA — reserved
IOVA requires the of_iommu→iommu_dma reserve path keyed to the target
IOVA, which does not exist here; do NOT mutate the DT for this. The
enforced invariant is in code instead: `ane_t6021_fw_alias_iova_ok()`
refuses any module DMA allocation (boot pool, rtkit EP rings; wired at
every dma_alloc_coherent site) whose [iova, iova+size) intersects the
alias window. The proper durable fix is an upstream apple-dart/of_iommu
reservation sourced from the DART vm-base — future work, not a DT edit.

## Implementation (this commit)

`ane/t6021/ane_t6021_fwload.c`: fw_load step 4 — after segment copy,
`ane_t6021_fw_alias_map()` reads the live RVBAR, requires the latched
branch, per-page:
  src = iommu_iova_to_phys(dom, fw_iova + off)   (must be valid+aligned;
       never virt_to_phys — the fw surface is non-contiguous, kcore-
       proven)
  assert iommu_iova_to_phys(dom, entry + off) == 0

any error. prot = READ|WRITE (+CACHE iff dev_is_dma_coherent, matching
the attrs dma-iommu used for the fw map itself). Remove path unmaps the
alias before dma_free_coherent. `ane->fw_alias_iova` added to the
device struct; stale "publication datum unevidenced / alias reviewed
OUT" header comment replaced by this contract.

2. The provider is AppleARMIODevice (not the perf controller):
   AppleARMIODevice::enableDevicePower(on,out,flags) (0x8c6f408)
   bounds-checks flags against the power-state count at [this+0xB0],

   message 0x05070004) — i.e. requestPowerState through the IORegistry

   (0x8c7c5dc) is a STUB returning 0xE00002C7 on this platform —
   device power does NOT flow through the perf controller.
4. Inside the same ANE blob, enableAneSysClock uses the pmgr accessor
   OBJECT at dev+0x190 with METHOD calls (vtable+16, args from
