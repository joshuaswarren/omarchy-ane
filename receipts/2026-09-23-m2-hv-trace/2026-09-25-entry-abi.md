# macOS 26/27 kernel entry contract (2026-09-25)

Off-box. No laptop was touched. The kernelcache that spins under the hv is the
macOS 27.0 (26A428) Mac14,6 kernelcache, sha256
`8304156fe05849a45f1c15807432e82cb0e8ac8cb9c883541889bf51287340fa`, 125059072
bytes, byte-identical to the `kernelcache mac14j` the hv run loaded. It has no
`com.apple.sptm` or `com.apple.txm` fileset entry. SPTM is not in this boot.

## The contract

The entry is the LC_UNIXTHREAD pc, `0xfffffe000c5a0000`, the start of
`__TEXT_BOOT_EXEC`. It dispatches on x0:

- x0 == 0: cold boot. x1 is the boot_args pointer, x2 is a handoff struct pointer.
- x0 == 4 or x0 == 5: SPTM entry paths. Not taken on the M2.
- anything else: secondary CPU. It looks up per-CPU data by MPIDR and spins on
  `cbz x21` at entry+0x10c while the table is empty. x21 is `[table+8]`.

m1n1's `HV.start` calls `hv_start(entry, bootargs)`, and the proxy places that
single argument in x0. x0 is therefore the boot_args pointer, which is none of
0, 4 or 5, so the boot CPU takes the secondary path and spins. The earlier run
that passed the boot_args pointer in x1 still spun because x0 was unchanged.
The field at boot_args+8 is `virtBase`; nothing in the entry reads it.

x1 is the boot_args pointer. The 27.0 kernel reads `[x1+0x60]` and `[x1+0x68]`
(deviceTreeP, deviceTreeLength), which is exactly where m1n1's `BootArgs_r3`
puts them. m1n1 already fills x1 correctly. What it never passes is x0 = 0 and
x2.

x2 points to a handoff struct. The entry checks, in order:

- `[x2+0]` must be `0xd00f000000000000`, or it spins on `wfe`.
- a versioned sub-struct at `x2+0x1a0`. version >= 7 makes the entry copy the
  sub-struct fields out to globals at `0xfffffe0007f48000+0x6c8` upward.
- bit 6 of the field at `x2+0x248` is copied to the global byte at `+0x778`.
  That byte must be non-zero, or the entry executes `udf #0` and the CPU dies.
- the field at `x2+0x1a8` is copied to a global the entry dereferences as a
  table count, so it must point at a readable zero word.

Every other field is a count or a pointer that the kernel null-checks or
range-checks before dereferencing. Zero fails those checks and the lookup
returns not-found. The consumers are at `0xfffffe000c5661b8` and
`0xfffffe000c58aae0`.

## The fix

`tools/m2hv_entry_abi.py`, an hv `-m` module. It writes the handoff struct into
the bootargs region at +0x1000 (past the boot_args struct, inside the mapped
0x4000-byte region) and rewrites the `hv_start` call to pass x0 = 0, x1 =
bootargs, x2 = handoff. It also passes x0 = 1 for secondary CPUs, so they take
the lookup path instead of re-entering cold boot. Load it only for a 26/27
kernelcache. A 13.5 kernelcache wants the stock x0 = bootargs contract.

No m1n1 source change and no rebuild: the module monkeypatches the proxy
client at run time. m1n1 upstream (AsahiLinux/m1n1, commits since 2025 and
issues 622, 651) has no work on a macOS 26/27 hv entry. The hypervisor doc
pins macOS 14.8.3 for M1-M3 and says SPTM is required only for M4 and newer.

## Run command

Bounded to 180 s. `KERNELCACHE` is the 27.0 Mac14,6 kernelcache named above
(sha256 `8304156f...`). The proxy client dir is the jwm1 m1n1 checkout at
commit 4184923.

```
M2HV_PREMOD=<omarchy-ane>/tools/m2hv_entry_abi.py M2HV_TIMEOUT=180 \
  tools/m2hv_catch_and_run.sh <PROXYCLIENT_DIR> <KERNELCACHE> <TRACE_MODULE> <OUTDIR>
```

The run.log line `entry abi: x0=0 x1=bootargs ... x2=handoff ...` confirms the
contract was applied. The boot CPU is past the spin once the vuart shows kernel
console output, or the trace shows execution past entry+0x10c.

## Next wall

Not SPTM and not TXM. The M2 kernelcache contains neither binary, and the
x0 == 4 and x0 == 5 paths are the SPTM entry and are not taken. Modern macOS
under the m1n1 hv is reachable on the M2.

The wall after this fix is the handoff struct's contents. The pointer fields
the entry copies to globals `0x6d0` through `0x7c8` are tables iBoot fills
(memory regions and object ranges). This fix hands the kernel empty tables, so
every lookup returns not-found, and the kernel panics at the first path that
needs a real one. Filling them means decoding each global and reading what the
M2's iBoot writes there. That is a bounded reverse-engineering task.

Two things to watch on the first run. The instruction at entry+0xc0
(`0xd4e00000`) is an Apple-proprietary EL1 instruction; it occurs 311 times in
the kernel, so the M2 executes it natively and the hv should not trap it. If it
does trap, `-e` surfaces it. And the boot CPU must publish per-CPU data before
the hv releases the secondary CPUs, or they wait forever in the lookup.
