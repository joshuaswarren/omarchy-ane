## Station table and per-station objects

  Table global 0xcb5c0: [count@", +8 = array of station pointers,
  indexed by station/endpoint id (w8 uxtw #3 peers).
  Station object (0x38 bytes, allocated in RTKit boot init 0x96934
  with `str wzr,[x0,#0x30]`; at allocation [x0] vtable 0x16c378,
  [x0+0x20]={list head +0x108, self}):
    +0x00  inner queue object (virtual target of all ops)
    +0x18 / +0x10 / +0x08  misc referenced objects (query fn 0x9a758)
    +0x20  shared-buffer descriptor table {rows, base} used by the
           properties query 0x9a7f0 (rows/stride math at 0x9a878-)
    +0x28 / +0x2b / +0x2a  flags (0x2b written with 1 or 2 states,
           0x2a checked in the suspend block)
    +0x2c  max message id seen / count (read by 0x9a944: `cmn w9,#0x13
           / ccmp w1,w8` bounds; entries laid out via a u16 bitmap
           [x+0x18] with 0x60-stride slots in [+0x10])
    +0x30  FLAGS: bit0 = ARMED/ATTACHED gate for send AND receive.

## Arm/disarm primitive

  0x9a988(w8=station_id, w1=arm)   bounds-checked trampoline
    count check vs [0xcb5c0]; <= count-1 -> 0x9a9a8(w0=..., w1)
  0x9a9a8:
    w1 != 0 (ARM):   virtual op w1=9  (attach, arg = struct {fn 0x9aa84,
                     self} paciza pair); then virtual op w1=1 (START);
                     then [st+0x30] |= 1 ; dsb sy ; then virtual op
                     w1=5 (post-start notify). Success = 0.
    w1 == 0 (DISARM): [st+0x30] &= ~1 (not dsb'd); virtual op w1=2
                     (STOP) with w=1. 
  0x9a944(st, id): per-id message-block lookup: bounds via [st+0x2c]
    and a u16 presence bitmap at [st+0x18] (ids < 0x1e direct map,
    0x12-0x2b shifted block), slot = [st+0x10] + idx*0x60. Ids are
    "message ids" within the station, consistent with the u8/u16
    ids seen in the send/recv wrappers.

## Who arms stations

  RTKit-internal message pump 0x98694 (called with the mailbox message
  buffer): for each message with type != 5 and != 4 it DISARMS then
  IMMEDIATELY re-ARMS the station ([msg+4]) — 0x9a988(id,0)+0x9a988(id,1)
  — then a virtual op w1=0xc ("drain") on the station's inner object,
  then re-broadcasts the control message to the endpoint [msg+8] via
  0x9ad28 with the 0xc0c00000|0x100000|R flag folded from [msg+0x54]
  bit 3, then acks (type 4 paths skip). 0x9b08c handles [msg+8]-side
  bookkeeping. This is the classic RTKit control-message pipeline
  where the HOST side drives queue wake/drain via control words; the
  firmware does not self-register by name.
  Whole-text scan: the ONLY arm site (store of [x+0x30] with `orr #1`)
  in the entire firmware is 0x9aa18 in the arm fn above, plus
  runtime state writers at 0x93694 (per-entry enable/disable switch in
  a table walker, arm toggled by entry type 1/2) and 0x93f84
  (an event/IRQ dispatcher path, sets arm + optional global hook
  0x1ccb80 blraaz + 0x9ca7c wake). Those two are the *station's own
  inner-queue* update paths, not RTKit-level arm.

## Consequence for the [q+8] construction gap

The ANE-side link object's [+0x10] endpoint id is a RTKit STATION id
(index into 0xcb5c0); stations are allocated at RTKit boot and armed by
the RTKit pump/control messages, not by ANE code. The remaining pin is
which ANE-side constructor allocates the chain
queue(+0x40) -> link(+0x08) with [link+0x10] = <station id> and what
station id the H2T CSNE channel uses. No name strings exist in the
payload for queue names, so identification must proceed structurally:
(1) the second-channel users 0x36138 (pop sibling 0x6464) / 0x385d0,
0x4bd2c (push) lead to the same queue class ctor; (2) 0x9b08c and
the handler registration at RTKit boot (0x96934) reveal the station
guest callback list, from which the CSNE station can be identified by
its handler pointing back into the 0x2bb34 evaluator vein.

Also decoded this pass:
  0x9a7f0: per-station properties query (out+0x10 status 3 when
    unattached, out+0x18 station id, out+0x1c.. records from the
    station's +0x20 descriptor table in 0x18-byte entries).
  0x963d0: vtable-tail fused lock/unlock call pair (used as mutex
    acquire/release around RTKit globals 0xcae40 / 0xa1...) — the
    earlier reads of it as "logging" were artifacts of the same shape;
    classify by the two-method offsets (+0x18 pre-call, tail-call
    into [+exact vtable slot]) rather than by name.
  0x9ad28 full body: armed-gate first (0x8000fff7 family errors),
    block alloc via 0x9a944, global 0xcae40 write of a paciza'd
    tracking record {0x93c98, block}, [0xcb0c0] core lock via
    0x9c78c/0x9c6bc, retry loop 0x94dcc/0x94e48 until accept, then
    the virtual send on the inner object (op w1=2, struct at sp:
    payload x19, ep w20, 0 at sp+0x10, 0x1@c=1) and completion via
    [inner+0x20] -> 0x9abfc. x2 = payload length or -1 for the
    short-record form.

Static disassembly only. No hardware was accessed.

## Addendum 3 — dispatcher, builder body, and the data-region reframe

Firmware SHA-256:
  32ce2ba5af65742d68e703db66430ca15e0132af7ca5e59ec9b743d7e9ca3f0c
Supersedes/adds to the sections above.

### 0x96458 — RTKit selector dispatcher (op 1..0xf)

pacibsp fn: switch on w1 selector (bounds sub w16 = w1-1, cmp 0xe; default
-> 0x9666c error 0x8000fffc), branch table looked up via 0x960e9c
(ldrsw x16, [x17, x16, lsl #2]; adr x17, 0x964cc; br x16). Case bodies
call virtual methods on the compiler-picked globals (0xcb0f8, 0xcb1608/,
0x1cdeb8, 0xcae40, 0xcb690, 0xcb7f8) — these are the RTKit OPS
subsystem objects; the opcode values the station class consumes in
virtual ops (1=START 2=STOP 5=notify 9=attach 0xc=drain 0xf=query,
previously assigned in 0x9a9a8) align with the selector domain.
Correction: 0x963d0 (called from the 0x963d0 cluster) is NOT a
standalone fused lock/unlock pair — it sits among dispatcher case
fragments; the receipt-2 classification for it is withdrawn. 0x96934
(selection unresolved — see below) is one of its case bodies.

### The 0x96934 case body — station boot, corrected framing

Body does: allocate 0x38 station, vtable 0x16c378; [st+0x30]=0;
loop reads ids/table from x26 = 0xcabc0 (stride x24 = x26+0xc; checked
id at [x24], 8-byte field ldur x9,[x24,#0xc] stored to slot[0]; slots
0x60-stride in [st+0x10]; presence bitmap strh at [st+0x18] indexed by
(id<0xe ? id : id-0x12) via ORR w11 = (i<<1)|1; word bitmap at [st+8]);
then register with service magic w0=0x436d6278 ("Cmbx") via 0x9cc94
with callback 0x9a7f0; allocate the 0x68 control entry (d0 template
from 0xb81b8/0xb81c0 = {00 00 00 00 00 00 00 00}/{00 00 10 00}),
linked into 0xcb690, [entry+0x28] = paciza(0x980a48), [entry+0x38]=0,
[entry+0x30]=0, [+0x19]=0 [+0x1a]=0xf [+0x54]=1, [+0x18]=1;
0x96228(0x1ccbb8); 0x9acb8(entry[8], paciza(0x98087c), entry);
0x9bb24(paciza(0x98694), entry) — the per-entry pump; 0x98854(entry[4]);
pump call 0x98694(entry, 1, 0x21). The +0x60/0x10 byte inside the
[E6] '0x54' byte is the byte copied from [0x1ccbb8] to [entry+0x5c].

### The data-region reframe (IMPORTANT for all prior reads)

fns like fn 0x8434 etc read slots 0xcabc8/0xcadf8/0xcae18/0xcae28/
0xcae40/0xcae08/0xcae30 via adrp+add+ldr — these are RELOCATED GOT
slots (runtime-patched); the DUMPED contents are PRE-RELOCATION
boot data, not runtime tables:
  0xcabc0..0xcadf0: 44 x 8-byte {u32 low, u32 kind-tag} entries
    with tag 0x100000 (43x), one 0x300000 at 0xcade8, terminator 0
    at 0xcadf0 — RELOCATION descriptors (rebase), not ep records.
  0xcadf8..: 8-byte {0x4000ac, 0} pattern — further relocs (the
    "0x400000-ish delta, section" shape).
  0xc61b0..0xc6358: records {u32 fmt-string-ptr (0xa2a80+,
    0xb4238+), u32 0x200000, u32 value}: value sequence 0x400,
    0x401..0x404, 0x7000, 0xff00, then 8-digit values 0x40021100,
    0x40024100, 0x4009019c..0x400901b0, 0x40094080/84, 0x40098100/08,
    0x400a0100/04, 0x400a4088, 0x400a4488, 0x400a4888, 0x400a4c88,
    0x400a708c. Read this as RTKit's rebase entry stream for a
    property/log REGION (asserts "boot chip minor rev …",
    "major 0x%x, minor 0x%x, program_offset_entry_num …", 'H','E','N',
    'A' package-magic asserts), NOT a register map and NOT the
    H2T/T2H channel catalog. The earlier "station-id register list"
    read is withdrawn.
Because 0x960e9c (the branch-table word array) lies beyond the raw
mapped code, the dispatcher's jump table itself resides in the
relocation-fixed region — resolving which case 0x96934 is requires
APPLYING the relocations first; until then treat selector identity
for 0x96934 as unresolved. Probable = attach (selector domain op 9
matches 0x9a9a8's attach op), but unproven.

### Standing consequences

- The [q+8] link-construction question remains open; RTKit-side
  "H2T/T2H channel table" as usually drawn does NOT exist in the
  raw image's static data — it is assembled at runtime by the
  loader/RTKit common code acting on these relocation records.
- For rung design, any claim tying a specific endpoint id to CSNE
  H2T must come from the runtime-resolved view, i.e. from DEALING
  WITH THE REBASE FORMAT, or from an m1n1/Asahi-side ANE firmware
  bring-up tool rather than more raw-offset reading.

Static disassembly/raw-image reads only. No hardware accessed.

## Addendum 4 — correct image address mapping and selector table

Correction to Addendum 3 above: its raw data reads used VA as a file offset.
That is wrong for this MH_PRELOAD. For __DATA (VM start 0xc0000, fileoff
0xc4000), the file offset is `0xc4000 + (VA - 0xc0000)` = VA + 0x4000.
The tables printed there from file offsets 0xcabc0/0xc61b0/0xcadf8 were
therefore unrelated bytes. Withdraw all Addendum 3 conclusions based on those
raw dumps, including the claimed 0xcabc0 relocation stream and the assertion
that no static station table exists. Re-read at the mapped file offsets before
assigning meaning. Firmware SHA-256 remains the same.

Also correction: the dispatcher jump table VA is **0x96e9c**, not 0x960e9c.
The instruction pair at 0x964c0/0x964c4 is `adrp x17,0x96000; add x17,x17,#0xe9c`.
Because code has fileoff 0x4000, the table is at file offset 0x9ae9c. Its
signed 32-bit deltas are relative to 0x964cc. Decoded selectors:

  1 -> 0x964d8; 2 -> 0x96914; 3 -> 0x964d8; 4 -> 0x966c4;
  5 -> 0x96770; 6 -> 0x9666c; 7 -> 0x9666c; 8 -> 0x96674;
  9..14 -> 0x9666c; 15 -> 0x96688.

Thus selector 9 does NOT dispatch to 0x96934; it dispatches to the shared
error return at 0x9666c. The function at 0x96458 returns at 0x96928; the
station-construction body begins separately at 0x9692c (no PAC prologue at
that address). The previous claim that 0x96934 is a case body of the 0x96458
switch and the guess that selector 9 identifies its registration are withdrawn.
The earlier observation that 0x9692c..0x96b20 allocates/builds station objects
and registers the Cmbx service remains a valid disassembly observation, but
its caller/dispatch selector still needs to be established.

The properly mapped data reads now show distinct structures: VA 0xcabc0 begins
with records containing 0x003000000009d3b3, 0x003000000009d3be,
0x003000000009d3c7, and 0x004000000009d3ce; VA 0xc61b0 begins a sequence of
{0x40000468, 0x00200000000b4b30}, {0x4000046c,
0x00200000000b4b30}, ...; VA 0xcadf8 begins scalar/layout data and then
0x00100000000b8105 / 0x00100000000b8128 / 0x801000000008a408. These are not
the previously reported strings/register list. Their encoded-pointer/tag
format is still unresolved; no channel identity inference is made here.

Offline only. No hardware accessed.

## Addendum 5 — station message-block descriptors (properly mapped)

Using the corrected __DATA mapping from Addendum 4, the four active rows
consumed by the loop at 0x96a28 are at VA 0xcabc0, stride 0x18. `x24` starts
at 0xcabcc; each iteration loads the block count from `[x24]`, the block key
from `[x24-4]`, and the encoded pointer/name from `[x24+0xc]`, then advances
by 0x18. The rows decode as:

  key 0, count 8, name VA 0x9d3b3 = "management"
  key 1, count 8, name VA 0x9d3be = "crashlog"
  key 2, count 8, name VA 0x9d3c7 = "syslog"
  key 0x20, count 8, name VA 0x9d3ce = "user1"

The name pointers are encoded in the image as `0x003000000009d3b3`,
`...d3be`, `...d3c7`, `0x004000000009d3ce`; the loader's runtime decoding is
not reconstructed here. The zero count at the next row terminates the loop.
This is strong evidence for four named message blocks in the station being
constructed, with keys 0, 1, 2, and 0x20. It does NOT identify the station's
global index or prove that any block is the CSNE H2T/T2H channel.

The per-block setup call is `0x925b0(block+0x28, count, 8)`. It computes and
stores the count+1, stride 8, allocates a `(count+1)*8` byte area, zeroes
entries, and initializes the block's pointer fields. This confirms that the
four names/keys are block metadata, not four station names or four separate
station objects. The station object is inserted into the global station
pointer array once, after the block loop.

The `0x96458` selector table remains as listed in Addendum 4. The station
builder at 0x9692c is outside that function (the dispatcher returns at
0x96928). Direct branch/call references to 0x9692c/0x96934 were not found in
the decoded text; its entry/caller and the value assigned to station+0x28
remain unresolved. Do not infer a station ID from the block keys.

Static image/disassembly only. No hardware accessed.

## Addendum 6 — builder is dispatcher success path; station slot 0

The statement in Addendum 5 that a direct caller/reference to 0x9692c was not
found is too narrow and is superseded here. `0x9692c` is an internal basic
block of the function beginning at 0x96458, reached by conditional branch,
not by BL. The selector table at VA 0x96e9c (file offset 0x9ae9c) maps
selectors 1 and 3 to 0x964d8. That shared setup case eventually calls
0x8d9f4 at 0x9665c; `cbz w0, 0x96830` (0x96660) enters the success path.
After the subsequent setup/virtual operations, `cbz w0, 0x9692c` at
0x9690c reaches the station construction block. Failure returns through
0x96910..0x96928. Selector 4's path ends through 0x96828 -> 0x96914; selector
5's path also returns through 0x96914. Do not attribute the station builder
to selector 9 (which maps to the shared error return).

Within this success block:
  - `0x9692c` allocates a 0x48-byte wrapper object, stores the global list
    linkage, then checks the station table at 0xcb5c0.
  - If the first pointer slot is already populated, it takes the existing
    error/cleanup path rather than constructing a duplicate.
  - Otherwise `0x96970` allocates the 0x38-byte station object; its fields
    are initialized, including `str q0,[x0,#0x20]`, which zeros the dword
    at station+0x28. At 0x96abc the object is stored in
    `[station_table_array + (station+0x28)*8]`; for this newly initialized
    object that index is 0. The static global table count at 0xcb5c0 is 8,
    so this constructs/populates slot 0 of an eight-slot station table.
  - That station's four active message-block descriptors are the keys and
    names listed in Addendum 5: 0/management, 1/crashlog, 2/syslog,
    0x20/user1 (each count 8).

This establishes the control-flow path and that this initialization pass
populates station slot 0. It still does not establish which station/block
the host binds to CSNE's `queue(+0x40)->link(+0x08)` path, nor that the
`management` block is CSNE H2T/T2H. Those require matching the host's runtime
endpoint/channel registration to this station's `Cmbx` service and the CSNE
evaluator. Static firmware evidence only; no hardware accessed.

## Addendum 7 — Cmbx service registration call contract

The call at 0x96adc is to the tiny wrapper at 0x9cc94, which sets `w1=0x300`
and branches to the common registration routine at 0x8d018. At the call site,
the arguments are:

  x0 = 0x436d6278 (service tag; bytes as stored in the register are
       78 62 6d 43, or "xbmC")
  x1 = set by wrapper to 0x300 (registration operation)
  x2 = paciza(0x9a7f0) (station properties/query callback)
  x3 = the station index loaded from [station+0x28], here slot 0

`0x8d018` checks nonzero tag and callback, allocates a 0x28-byte service
record, stores `{tag@+0, operation@+4, callback@+8, context@+0x10}`, and links
it into the global list rooted at VA 0xcaf40 (list lock at +0x88). It returns
zero on success. This confirms that the `Cmbx` registration is a named service
registration carrying the station-slot context, not itself construction of
the queue's RTKit link object.

Thus the identified firmware-side chain is now: dispatcher selectors 1/3
success -> station slot 0 -> four message blocks (management/crashlog/syslog/
user1) -> Cmbx op 0x300 registered with callback 0x9a7f0 and context 0.
There is still no evidence tying that service to the separate queue link at
`[q+8]`, or tying any one block to the H2T/T2H CSNE path. The Linux run's
eight channel records are a different layer and cannot be mapped from this
service registration alone.

Static disassembly only; no hardware accessed.

## Addendum 9 — queue consumer vtable identity (structural, not named)

`0x35128` installs the encoded vtable at VA 0xc76f0 (`adrp x16,0xc7000; add
x16,#0x6f0; add x16,#0x10; pacda; str [object]`). Under the corrected data
mapping, the vtable bytes are at file offset 0xcb6f0. Its first virtual slots
are encoded pointers whose low 32-bit targets include 0x35e90, 0x35e94,
0x6158, 0x6168, 0x35eb0, and later 0x35eb4 at vtable offset +0xc0 (slot 22
after the two-word vtable header). The body at 0x35eb4 is the already-traced
consumer that pops from `[object+0x190]` via 0x637c. This ties the pop method
and the 0x35128 initializer to one concrete firmware class/vtable, although
no reliable class name has been recovered from the image.

The constructor also stores its x4 input at +0x190 and, when `[x20+8]` is
nonzero, copies `[x20+0x28]` to +0x1d0. That confirms the two queue references
are fields of this class instance, not coincidental offsets in unrelated
objects. It still does not reveal who creates the x20 input or which queue
endpoint is attached. The `CAneEngineExeLoop` source-path string exists in the
image, but no direct reference tying that string to vtable 0xc76f0 has been
found; do not use that name as a proven class attribution.

Static image/disassembly only; no hardware accessed.

## Addendum 10 — creator path for the 0x35128 queue input

The initializer's x4 input is no longer an unidentified factory argument.
The path is:

  0x43f4: create/get the object at global +0x668
  0x440c: `0x1734c(global_service_object, 1)` -> slot 1 at `[base+0x1f8+8]`
  0x441c: `0x1734c(global_service_object, 3)` -> slot 3 at `[base+0x1f8+24]`
  0x4450: call 0x32438 with x4=slot 1 and x5=slot 3
  0x32438: argument shuffle passes slot 3 as x6 to 0x2a678
  0x2a678: saves x6 in x24; at 0x2abf0 calls 0x35c20 with x4=x24
  0x35c20: tail-branches to 0x35128, whose first body instructions save x4 as x20

Thus `[x20+0x28]` in the initializer is specifically the `+0x28` field of
the service object's slot-3 result, not a station-slot value supplied by the
Cmbx registration. The lookup helper at 0x1734c bounds-checks selector <= 3
and returns the corresponding pointer from the four-entry array at +0x1f8.
The name/type and construction history of that slot-3 service object are not
yet established; in particular, this does not identify it as CSNE H2T/T2H or
map it to a Linux channel record. It does, however, close the previously
unknown immediate creator/input chain for the queue consumer. Static image
and disassembly evidence only; no hardware accessed.

## Addendum 8 — queue consumer fields in the 0x35128 initializer

The initializer beginning at 0x35128 (body at 0x3512c) receives x4 in x20 and
stores it at `[parent+0x190]` (0x35200). After checking `[x20+8]`, it loads
`[x20+0x28]` and stores that pointer at `[parent+0x1d0]` (0x35240..0x3524c);
it also reads `[x20+0x38]` as a size/capacity-like value for a bounds check.
The corresponding push sites are:

  0x38570: load [parent+0x190], then pass it to 0x62e0
  0x4bd2c: load [parent+0x1d0], then pass it to 0x62e0

At 0x38570, linked-vs-fallback choice is made by testing `[[parent+0x190]+8]`;
the queue push at 0x62e0 receives the selected message pointer/length. At
0x4bd2c the payload has a different producer but uses the same queue primitive;
the code then checks `[[parent+0x1d0]+8]` to branch on link presence. This is
consistent with two queue references within the parent object: one retained
as the constructor argument, and another nested queue pointer sourced from
that argument's +0x28 field.

This does not identify the creator of the x20 argument, prove that this is the
CSNE drain queue, or recover either queue's `[q+8]` link endpoint ID. The
initializer has no direct BL callers in the decoded firmware text, so its
invocation appears indirect (e.g. class/vtable path); the upstream factory and
runtime registration are still the next trace targets. Static disassembly
only; no hardware accessed.
