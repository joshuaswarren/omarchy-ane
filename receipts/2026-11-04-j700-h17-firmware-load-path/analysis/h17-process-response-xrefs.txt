H17 processCommandResponse dispatch trace (offline disassembly)
==============================================================

Source kernelcache SHA-256:

Receive and dispatch path
-------------------------
In aneInterruptHandlerPriv at 0xfffffe0008f582b4..0xfffffe0008f582c8, the
unidirectional receive primitive receives pointers to stack outputs:
  x1 = sp+0x50 (message ID output)
  x2 = sp+0x48 (message size output)
  x3 = sp+0x40 (payload output)
The primitive at 0xfffffe0008ef8a10 strips both low bits from the slot word
and stores that resulting message ID through x1.

When the channel index does not match the three specially handled indices
tested at [device_state+0x1f8], +0x1fc, and +0x20c, control reaches
0xfffffe0008f585ac. There it loads x2 from [sp+0x48] and x1 from [sp+0x50],
loads x3 from [sp+0x40], sets x0 to the device object, and calls
processCommandResponse at 0xfffffe0008f585b8. Thus the received queue message ID
is directly passed as processCommandResponse's x1 match token; length and
payload are passed as x2 and x3. This closes the host-side queue-token
propagation path.

Correction to prior scan
------------------------
The previous scan receipt incorrectly reported no direct reference. Its
Capstone comparison treated branch immediates as unsigned canonical VAs,
whereas Capstone returned a sign-extended relative value for this high kernel
address. It therefore missed the call above. The raw-literal/vtable observation
at 0xfffffe000c7c4dc8 was not needed to establish this direct call.

Evidence limits
---------------
This proves host-side received slot-ID -> processCommandResponse x1 flow in
the retained kernelcache. It does not prove what token value firmware returns,
how that token relates to the inner CSNE command code at command+4, the PING
payload/reply schema, or safe command eligibility. Static disassembly only;
no hardware access or device behavior is claimed.
