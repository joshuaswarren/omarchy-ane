## Confirmed facts (measured / pinned)

1. The ADT has **no separate ANE mailbox node**. The ane node itself is
   `compatible=iop,ascwrap-v6` with five windows: `ane 0x311400000+0x6c000`,
   `ane_alt 0x311050000+0x4000`, `engine 0x310000000+0x2000000`,
   `pmgr 0x2d0700000+0x18000`, `pmgr_ps 0x2d0724000+0x4000` (S1, line 229).
2. The ane node carries **five interrupts in ADT order: 507 506 509 508 524**,
   gates `ANE_CPU ANE-SYS-V`, ane-type **176** (S1, line 229).
3. `dart-ane` is `dart,t8110` with four ttbr windows at `0x311800000..0x311820000`
   (`+0x4000` each) and `0x311804000`, IRQ **525** (S1).
4. The ADT summary declares **j613 same as j433** (S1, line 239): J433s, J434,
   J504, J613 and J615 share the identical ane node text, so the block below
   covers the whole family.
5. Scott's community row (S8) confirms a **running Linux device tree** on J613
   exists (deep dive, 2026-10-02) — its content is pinned by hash
   `3bec43ce…` but the t8122.json cites S8 only for `boards[3]`; no mailbox
   field in the json cites S8 today.
6. The PMGR facts are complete (S1): ANE_SYS `0x2d0700438`, parents `LMX4`;
   ANE_MPM/CPU/TD/BASE at `0x2d070c000/8/10/18`; one ANE_CPU domain child of
   ANE_TD+ANE_CPU.

## Recorded inference (t8122.json, marked INFERENCE — not measured)

- Mailbox compatible is expected `apple,t8122-asc-mailbox` +
  `apple,asc-mailbox-v4`: every other T8122 ASC mailbox in S4
  (smc, aop, mtp, ans; t8122.dtsi:833-1069) uses that pair.
- Mailbox window is expected **`0x311408000+0x4000`** (engine + 0x1408000,
  the ASC-wrapper + 0x8000 shape every T8122 ASC mailbox uses; the earlier
  claim of `0x311050000` — reg[1], the T6021-style RVBAR offset — had no
  source and is withdrawn).
- The four-interrupt block **506..509** is expected to be the mailbox, in ADT
  order `send-empty, send-not-empty, recv-empty, recv-not-empty` (the role
  order every T8122 ASC mailbox in S4 names). **524** = the DART IRQ
  (525 minus one; T6021 analog: ANE IRQ 884 = DART 885 − 1). The ADT does not
  name the roles.
- ASC layer: ane_t6021-like (CPU_CONTROL at wrapper + 0x44), RVBAR at
  reg[1] = engine + 0x1050000, DART four-window shape at engine + 0x1800000;
  no new ASC-IOP client.

## Missing facts — what the first m3air run must answer

1. **Does the running device tree name an ANE mailbox node?** Scott's S8 is a
   running-DT read; if his dump (or a fresh one from the m3air boot) prints a
   mailbox node or `interrupt-names` under the ane node, that resolves the
   compatible, the window, and the four roles directly from S8-grade evidence
   — no probing needed. This is the first thing to capture.
2. **The four roles of 506/506-neighborhood 506..509** (send-empty,
   send-not-empty, recv-empty, recv-not-empty — which ADT slot is which): not
   in the ADT (unnamed) and not in S4 (the kernel tree has no ANE mailbox
   node). Answerable by `interrupt-names` in the running DT, or by firing the
   mailbox and observing which line fires.
3. **Does the preloaded M3 Linux firmware send RTKit HELLO?** Not measured
   (the T6021 13.5 image never did; its working path is the legacy ChMan
   ring). This decides mailbox-v4 vs the legacy ChMan ring for T8122.
4. **Confirm the mailbox window `0x311408000+0x4000`** by mapping it through
   the driver (non-posted `of_iomap`/`ioremap_np` — see the M3 Pro PWGATE
   posted-mapping reset finding) and reading a mailbox register.
5. **RVBAR `0x311050000` (reg[1])** confirmed by a successful core start
   through it.
6. Power gates `ANE_CPU ANE-SYS-V` + the ANE_BASE domain ordering already
   work through the non-posted mapping (M3 Pro finding); re-check on the
   m3air boot only if the core start fails.
